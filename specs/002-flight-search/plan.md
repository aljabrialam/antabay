# Implementation Plan: Flight Search

**Branch**: `002-flight-search` | **Date**: 2026-08-28 | **Spec**: [spec.md](spec.md)

## Summary

Implement a `FlightSearchService` that submits a one-way search to the Atlas `search.do`
endpoint using parameters from a confirmed `JourneyRecord`, persists the raw response,
maps each routing to a `FlightOption` record (with `fid`, `routingIdentifier`, freshness
timestamps, leg structure, and scarcity signals), decrements the journey's call budget, and
returns a `SearchResult`. Rate-limit rejections are handled without retry. Empty results are
valid outcomes.

## Technical Context

**Language/Version**: Python 3.11+ (matches Feature 001 and constitution)

**Primary Dependencies**:
- `httpx` >= 0.27 — async-capable HTTP client; already in `backend/pyproject.toml`
- `sqlalchemy` >= 2.0 — storage layer; already present
- `pydantic` >= 2.0 — data models; already present
- `pytest` + `pytest-recording` (VCR) — Tier 1 cassette tests; already present

**Storage**: SQLite (development/test) via existing `JourneyRepository` infrastructure;
schema extended with `flight_options` and `search_records` tables.

**Testing**: pytest; VCR cassettes for Tier 1 (recorded from Tier 2 live sandbox);
`fixtures/atlas/sel_tyo_search.json` already committed as seed fixture.

**Target Platform**: Python backend service (same process as Feature 001)

**Performance Goals**: Search response recorded and mapped within 500ms of receipt;
remaining usable time computation accurate to ≤1 second.

**Constraints**:
- Atlas `search.do` rate limit: 10 QPS — enforced by `FlightSearchService`, not by caller
- No retry after 429; honour `retryAfter` interval
- `fid` and `routingIdentifier` preserved byte-for-byte (Constitution I)
- Raw response persisted before any processing (NFR-001)
- No field modification or enrichment (Constitution I, FR-011)

**Scale/Scope**: Single backend service; one `search.do` call per invocation; up to 30
routings per response (observed maximum on SEL→TYO route).
